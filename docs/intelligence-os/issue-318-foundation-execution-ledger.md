## Plain-English program truth

### What Nested Objects is trying to accomplish

Nested Objects is building an inspector-first membership business that helps field inspectors reach useful outcomes: understand the work, find credible firms and opportunities, operate profitable routes, and know when a paid plan creates real additional value. Behind that experience, one operating system should reconcile identity, membership, billing, behavior, marketing, opportunity, and search data so Autumn can see what is true, approve consequential actions, and improve conversion without misleading promises or uncontrolled automation.

### What has been implemented in plain English

The member site now has clearer Free-offer language, a three-firm Free preview, direct Free signup, an onboarding guide, owner-only member profiles, and a private conversion-event ledger. The Intelligence OS has a separate runtime, durable staging tables, deterministic specialist logic, three operating-review workflows, read-only sensor adapters, an owner-only review screen, duplicate-run protection, approval/rejection records, and trace links. Synthetic Preview acceptance proved the main review path without using real member data, models, email, or external mutations. The current local review branch also hardens rate-limit/contact failure truth, removes embedded Supabase credentials from 34 tracked maintenance scripts, and replaces the blanket tool lock with two conservative browser-only calculators; those branch changes are not deployed yet.

### What has changed for members

Visitors are no longer promised broad Free directory search. Free members see at most three actionable firm records and locked/sanitized previews beyond that. New inspectors can register directly and receive a first-use guide. Inspector profile browsing is restricted so a member sees only their own profile, and the login regression introduced during those access changes was repaired. Current Production still applies the blanket member-tool lock. The local `ACCESS-001` repair makes the income scenario planner available to every recognized signed-in member plan and route economics available to Elite/Agency while keeping unverified connected tools off; it requires Preview and Production verification before it changes member experience. The member-side Agency offer remains visible locally, but new purchase is paused until its seats, roles, and admin controls are verified; existing Agency members retain their reviewed calculator access.

### What has changed behind the scenes

Nested Objects now has staging schemas for canonical members, daily metrics, signals, experiments, runs, tasks, actions, events, workflow steps, operating reviews, sensor observations, approvals, outcomes, measurements, and learnings. The runtime can persist synthetic workflows durably, reuse a business key, keep healthy reviews quiet, limit weekly priorities, and show Autumn an approval surface. Conversion events are server-owned and browser grants were removed. The broader Outseta, Supabase, ActiveCampaign, analytics, and billing truth is still fragmented and must be reconciled rather than assumed.

### Which agents are real versus extension contracts

The Operations Orchestrator, Revenue Agent, Growth Agent, Industry Intelligence Agent, and Marketing Agent contain real deterministic logic. The Orchestrator and overall workflows produced substantive synthetic Preview results. Revenue, Growth, Marketing, and Industry behavior is proven only by local non-empty fixtures; the accepted Preview supplied them empty inputs, so it proved plumbing rather than their business analysis. The Opportunity, Inbox/Member Success, SEO/AEO, Lead/Firm Acquisition, Product, and Engineering/Codex names are extension contracts only; they do not yet perform their named jobs. A generic guarded OpenAI adapter exists, but no agent has a model-enabled verification.

## Status semantics

Only these values are allowed in the canonical matrix:

| Status | Meaning |
| --- | --- |
| `planned` | Requirement is defined; a working implementation is not yet evidenced. |
| `in_progress` | Some real implementation or reconciliation exists, but material required behavior remains. |
| `implemented_unverified` | Working code appears present, but the relevant execution or environment has not been validated. |
| `validated_local` | Current-source tests or a local fixture execution passed. |
| `validated_staging` | The relevant staging schema or behavior was actually validated in staging. |
| `verified_preview` | The behavior was actually exercised on an identified Vercel Preview. |
| `production_live` | The behavior was verified in the existing Production environment with explicit evidence. |
| `blocked` | Progress requires a missing dependency, authority, source, or decision. |
| `deferred` | Autumn intentionally postponed the work. |
| `superseded` | A later decision or implementation replaced this item; history remains. |

Composite rows take the lowest defensible status for their full requirement. A lower status does not erase a deployed sub-capability; the evidence column records that nuance.

## Agent maturity inventory

Maturity is the highest rung actually evidenced, not the intended destination:

1. `contract_only` — types, registration, interface, or placeholder only.
2. `deterministic_v1` — real business logic runs against fixtures without a model.
3. `model_capable` — a guarded model adapter is attached to the agent, though it may be disabled.
